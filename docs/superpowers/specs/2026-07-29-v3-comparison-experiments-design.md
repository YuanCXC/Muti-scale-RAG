# v3 对比实验重写设计

## 1. 背景与目标

`exp_v3` 当前包含 Proposed 方法及其消融实验，但缺少统一基于 v3 评测框架实现的外部基线。现有 `new_experiments_v2` 虽包含相关实验，但其代码结构、并发方式和结果格式与 v3 不一致，不能直接作为公平对比结果。

本次工作将在 `exp_v3` 中重写以下 5 个基线实验：

1. Semantic RAG
2. Rerank RAG
3. GraphRAG
4. KG-RAG
5. MacRAG

同时新增 1 个结果汇总脚本，读取上述基线与已有 Proposed 结果，生成统一对比表。

## 2. 范围

### 2.1 包含内容

- 新增 5 个完全独立、可单独运行的基线脚本。
- 每个脚本自包含配置、资源加载、检索、生成、语义评判、统计和结果写入逻辑。
- 检索与生成采用分阶段执行。
- LLM 活跃请求上限默认设为 200。
- 支持检索缓存、断点恢复、单样本重试和检查点保存。
- 新增 1 个离线结果汇总脚本。
- 统一数据抽样、评测指标、输出字段和命令行参数。

### 2.2 不包含内容

- 不修改 Proposed 或现有消融实验的算法。
- 不运行正式全量实验。
- 不新增公共基线核心模块，5 个基线脚本之间不得互相导入。
- 不编写或运行单元测试、集成测试。
- 不将 Proposed 重复嵌入 5 个基线脚本。

## 3. 文件设计

在 `exp_v3` 下新增：

| 文件 | 职责 |
| --- | --- |
| `semantic_rag_concurrent200.py` | 运行 Semantic RAG 基线 |
| `rerank_rag_concurrent200.py` | 运行 Rerank RAG 基线 |
| `graphrag_concurrent200.py` | 运行 GraphRAG 基线 |
| `kg_rag_concurrent200.py` | 运行 KG-RAG 基线 |
| `macrag_concurrent200.py` | 运行 MacRAG 基线 |
| `aggregate_comparison_results.py` | 汇总 5 个基线与 Proposed 结果 |

5 个实验脚本在运行时完全独立。允许脚本内部存在相同的基础数据结构和评测代码，以换取可复制、可单独审阅和无隐式依赖的实验实现。

## 4. 基线算法定义

### 4.1 Semantic RAG

1. 在句子级向量库中召回 `k1` 个候选。
2. 按标题去重。
3. 按原始相似度排序并保留 `k3` 个证据单元。
4. 不使用重排序、图扩展、父级回升或摘要补充。

### 4.2 Rerank RAG

1. 在句子级向量库中召回 `k1` 个候选。
2. 使用统一重排序器对候选重新打分。
3. 按标题去重并保留 `k3` 个证据单元。
4. 不使用图扩展、父级回升或摘要补充。

### 4.3 GraphRAG

1. 在句子级向量库中召回候选并按标题去重。
2. 取前 `k3` 个标题作为图扩展种子。
3. 在结构图中进行最多 `hmax=2` 跳扩展。
4. 合并种子与扩展证据。
5. 按统一上下文 token 预算选择最终证据。
6. 不使用 Proposed 的自适应路由或语义图协同策略。

### 4.4 KG-RAG

1. 分别执行句子级向量召回和关键词召回。
2. 合并候选并执行统一重排序。
3. 取前 `k3` 个候选作为知识图扩展种子。
4. 执行固定 1 跳图扩展。
5. 合并种子与扩展证据，并按统一预算选择最终证据。
6. 不使用复杂度驱动的跳数选择。

### 4.5 MacRAG

使用与 v3 一致的查询复杂度评分，但只用于固定的尺度切换：

- 低复杂度：句子级向量检索。
- 中复杂度：句子级与段落级候选混合后重排序。
- 高复杂度：段落级向量检索。

最终证据受统一 token 预算和 `k3` 数量限制。该方法不使用图扩展、父级回升或摘要补充。

## 5. 公平性约束

所有方法使用相同的：

- HotpotQA 数据文件。
- `sample_size`、`random_seed` 和抽样顺序。
- 向量库、文档库、图数据库连接配置。
- 生成模型、生成提示和最大重试次数。
- 语义评判模型、评判提示和拒答后处理。
- 上下文 token 预算。
- 检索指标与语义指标计算方式。
- 结果精度和 CSV 字段命名。

基线脚本不得调用 Proposed 的自适应路由、双图协同、选择性父级回升或摘要证据补充逻辑。

## 6. 分阶段并发设计

### 6.1 检索阶段

- 将全部样本提交给检索线程池。
- 线程数由 `--retrieval-workers` 控制，默认值与
  `adaptive_multiscale_rag_ablation_concurrent200.py` 保持一致。
- 涉及 API 重排序时，使用独立信号量控制并发。
- 每个样本最多重试 3 次。
- 单样本失败时生成空证据结果并记录错误，不终止整个实验。
- 支持将完整检索结果序列化到缓存。

### 6.2 生成与评判阶段

- 仅在检索阶段完成后启动。
- 生成和语义评判共享 LLM 并发信号量。
- `--llm-concurrency` 默认值为 200。
- 生成失败时记录尝试次数和错误信息。
- 评判失败时保留可用的确定性指标，并记录评判错误。
- 按固定间隔写入检查点，降低长时间运行的结果丢失风险。

## 7. 命令行接口

5 个基线脚本统一支持：

- `--sample-size`
- `--retrieval-workers`
- `--llm-concurrency`
- `--rerank-concurrency`
- `--generation-max-retries`
- `--judge-max-retries`
- `--no-generation`
- `--no-judge`
- `--no-neo4j`
- `--context-budget`
- `--retrieval-cache-dir`
- `--skip-retrieval`

只与特定算法相关的参数保留在对应脚本中。例如，GraphRAG 暴露最大跳数和图邻居上限，MacRAG 暴露复杂度阈值。

## 8. 单个实验输出

每个实验创建独立时间戳目录，目录前缀包含方法名。统一写出：

| 文件 | 内容 |
| --- | --- |
| `result_summary.csv` | 方法级聚合指标 |
| `semantic_records.csv` | 逐样本生成与语义评判记录 |
| `comparison_by_type.csv` | 按 HotpotQA 问题类型聚合的指标 |
| `details.json` | 完整逐样本结果与统计 |
| `config.json` | 本次运行的完整配置 |
| `checkpoint.json` | 运行中的可恢复检查点；成功结束后仍保留 |

核心汇总指标包括：

- Recall
- Precision
- F1
- Correctness
- Faithfulness
- Answer Relevance
- Context Relevance
- 平均上下文长度
- 检索延迟
- 图扩展节点数
- 生成成功率
- 拒答率

## 9. 汇总脚本设计

### 9.1 输入选择

汇总脚本支持两种输入方式：

1. 默认模式：在 `exp_v3/results` 中为每个方法选择最新且结构完整的结果目录。
2. 显式模式：通过命令行分别指定 5 个基线目录和 Proposed 目录。

Proposed 目录必须同时满足：

- 存在 `result_summary.csv` 和 `details.json`。
- `result_summary.csv` 中存在 `Proposed` 方法行。
- `details.json` 中存在 Proposed 的逐样本结果。

### 9.2 一致性校验

汇总前校验：

- 方法名唯一且符合预期。
- 样本数一致。
- 样本 ID 集合一致。
- 随机种子一致。
- 关键指标列完整。
- 结果明细可以解析。

默认情况下，任一校验失败都会终止汇总并给出明确错误。只有使用显式宽松参数时，才允许对共同样本取交集；宽松模式必须在输出元数据中记录。

### 9.3 汇总输出

汇总脚本创建独立时间戳目录并写出：

| 文件 | 内容 |
| --- | --- |
| `comparison_summary.csv` | 5 个基线与 Proposed 的总对比表 |
| `comparison_by_type.csv` | 按 Bridge、Comparison 等问题类型分层的对比表 |
| `comparison_details.json` | 合并后的逐样本结果 |
| `manifest.json` | 输入目录、校验结果、汇总时间和运行参数 |

总表方法顺序固定为 Semantic RAG、Rerank RAG、GraphRAG、KG-RAG、MacRAG、Proposed。

## 10. 错误处理

- 缺少数据文件、向量库或必要环境变量时，在资源加载阶段直接失败并指出缺失项。
- GraphRAG 和 KG-RAG 默认要求 Neo4j 可用；传入 `--no-neo4j` 时允许降级，但必须在配置和结果中标记降级状态。
- API 重排序失败时按既定次数重试；最终失败后回退到确定性本地排序，并记录回退原因。
- 单条生成或评判失败不会删除该样本；结果行保留错误字段。
- 汇总脚本不静默忽略损坏、缺列或样本不一致的结果。

## 11. 交付检查

根据本次约定，不编写或运行测试。仅执行以下基本检查：

1. 对 6 个新增脚本执行 Python 语法编译检查。
2. 分别运行 6 个脚本的 `--help`，确认命令行入口可启动。
3. 检查 5 个基线脚本没有互相导入。
4. 检查新增文件未修改现有 Proposed 与消融实验。

上述检查不连接真实 API、向量库或 Neo4j，也不代表正式实验结果有效。

## 12. 验收标准

- `exp_v3` 中存在 5 个完全独立的基线实验脚本。
- 每个脚本只运行自身基线，且采用检索与生成分阶段执行。
- LLM 活跃请求默认上限为 200。
- 5 个脚本的指标、抽样和结果格式与 v3 Proposed 保持一致。
- 第 6 个脚本可以严格汇总 5 个基线与已有 Proposed 结果。
- 汇总结果可追溯到具体输入目录和配置。
- 基本语法编译与 `--help` 检查通过。
